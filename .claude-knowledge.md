## What Jarvis is

A voice/chat assistant: an Electron desktop app (window) + a Python backend (`app.py`, the brain) talking over a
local WebSocket. Also reachable from a paired phone (`phone_control.py` + `phone_client.html`), with optional
"take control" computer automation (`computer_use.py` + `screen_mac.py`/`screen_windows.py`/`winctl.py`).

## Architecture map

- **`main.js`** — Electron main process. Creates the window, owns the system tray, the computer-control overlay
  (glowing edge + Pause/Stop bar shown while Jarvis drives the mouse/keyboard), login-item registration.
- **`backend.js`** — spawns/restarts/stops the Python backend (`app.py`) as a child process, picks the port/token.
  `Backend.start()` does NOT block on the backend actually being ready — it returns once the port is picked and
  the child is spawned; `onState('running')` fires later once the port accepts connections.
- **`app.py`** (~4400 lines) — the whole backend. Top-level flow at the bottom (`if __name__ == "__main__":`):
  starts the WS server thread, phone server (if enabled), several daemon background threads (AI connection check,
  device refresh, local-AI backup, timers, telemetry, weather), then **`main_loop()`** — the one loop that drains
  both typed input (`typed_inputs` queue) and voice (`listen()`), routes through `handle_direct_command()` first,
  falls through to `ask_jarvis()` (the LLM, with tool-calling) otherwise.
- **`handle_direct_command(text)`** — a long if/elif chain of ~45 pattern-matched commands that bypass the LLM
  entirely (timers, opening apps, Spotify, computer control, documents, calendar, etc.). See the published
  reference doc (link below) for the full list.
- **`TOOL_FUNCTIONS`/`TOOLS`** — the LLM function-calling schema; invoked only when no direct command matched.
- **`computer_use.py`** — the "take control" engine: `ComputerTask.run()` observes the screen, asks the AI for
  one action at a time, executes it, reports state. `Environment` is the abstract action interface;
  `screen_mac.py`/`screen_windows.py` implement it per-platform.
- **`phone_control.py`** + **`phone_client.html`** — phone pairing (6-digit code, QR-link-based) and an
  already-built real text-chat UI (`chatInput`/`chatSendBtn`, not just voice) once paired. Reconnecting an
  already-paired phone normally goes through a **push notification** (`start_phone_session()`), not a QR code —
  the QR/code flow is ONLY for the very first pairing.
- **`errors.py`** (new this session) — a dependency-free pub/sub error bus. Any module calls `errors.report(...)`
  (or `app.py`'s shorter alias `report_error`); `app.py` is the one subscriber that shows it as a toast in the
  window (`{"type": "backend_error", ...}` → `renderer.js`'s `showErrorToast`). Queues as `pending_errors` if no
  window is connected yet, replayed on connect (same pattern as `pending_alerts`).
- **`action_log.py`** (new this session) — structured JSONL log (`logs/actions.jsonl`) of every direct command
  and AI tool call with its outcome, separate from the casual chat transcript (`session_file` in `app.py`).
- **Published reference doc**: https://claude.ai/artifact/SBZbDXgTyc6D7cvZVymSLV — "Jarvis Command Reference",
  every direct command / AI tool / phone command / computer-control action, one table per category. **Keep this
  updated whenever a command/capability is added, removed, or changes behavior** — standing instruction from the
  user, not a one-off.

## Testing

- `tests/` uses `sandbox.py`, which mocks platform-level actions generically (regardless of which function calls
  them), so most intent/routing changes need zero sandbox changes.
- Run with `./venv/bin/python -m pytest -q` (plain `pytest`/`python3` on this machine resolve to a pyenv Python
  with no packages installed — always use the project's `venv`).
- 370 tests passing as of the last full run this session. `test_intent.py` covers direct-command routing most
  directly; `test_computer_use.py` the take-control engine; `test_phone_app.py`/`test_phone_control.py` phone
  pairing/sessions.
- No dedicated tests for `screen_mac.py`/`screen_windows.py` directly (real OS APIs, hard to unit test).

## Non-obvious design decisions / gotchas found this session

- **Platform action implementations used to prefer invisible/programmatic shortcuts** (AX `AXPress`/`AXFocused`
  on Mac, UI Automation `Invoke`/`SetFocus` on Windows, `NSWorkspace.activateWithOptions_` for window switching,
  direct `open -a`/`start` for app launching) over real mouse/keyboard simulation, because they're faster/more
  reliable. **Fixed this session**: every "take control" action now uses a real, visible click/keypress — see
  `focus_element`/`press_element`/`switch_window`/`open_app` overrides in `screen_mac.py`/`screen_windows.py`.
  `switch_window` now clicks the target's actual on-screen window if visible, else does real repeated Cmd+Tab /
  Alt+Tab presses (never held — both platforms only commit the switch on modifier-key *release*, so it's a loop
  of quick full press-then-release, not one held chord). `open_app` now opens Spotlight/Start-menu search with
  real keystrokes, falling back to the old direct launch only if that doesn't find a match.
- **`greet_on_startup()`/`greet_after_voice_launch()` used to run synchronously before `main_loop()` started** —
  since they wait for the window to connect AND block on `speak()` finishing the TTS playback, this delayed
  *all* chat (typed input included) until the spoken greeting finished. Fixed: now run in a background thread.
- **The local-AI backup (Ollama) used to download/run unconditionally on every startup**, even with a working
  Groq key, "just in case." Fixed: now lazy — only starts the first time a real Groq call fails
  (`groq_chat()`'s existing `LocalAIUnavailable` → `local_ai_status_reply()` → `start_background()` chain already
  did this reactively; the eager startup call was redundant on top of it).
- **Some "hidden error" spots already have dedicated, purpose-built UI** — don't double-wire these with the
  generic error toast: mic problems (`report_mic_problem()` → `{"type": "mic", ...}`, a status pill), local-AI
  setup failures (`local_ai_manager.state` → the auto-opening "AI setup" panel in Settings), Settings save
  errors (`{"type": "settings_error", ...}`). The generic `errors.report()` toast is for everything else that
  used to be print-only.
- **iOS Web Push only works from a page added to the Home Screen in real Safari** — never a plain Safari tab,
  never an in-app browser (e.g. opening the Jarvis link from inside WhatsApp). That in-app-browser case also has
  no access to Safari's localStorage, so it looks like a brand-new unpaired phone every time even after a
  successful pairing elsewhere. This was the root cause of a "No pairing request right now" loop diagnosed this
  session — not a code bug, a platform restriction. Fix is user-side: open in Safari, Add to Home Screen, enable
  notifications from there.
- **Spotify's own Cmd+K (Ctrl+K) quick-search shortcut** is more reliable than vision-model clicking for finding
  Spotify's search bar (`spotify_local.py`'s `click_search_bar()`) — a small local VLM missed the thin
  placeholder text often enough to be the most common "I don't see the search bar" failure.
- **`_SERVICE_NAMES` regex matching needs `.lower()` on its input explicitly** — it has no `re.I` of its own, by
  existing convention (same as its use in `is_new_command()`), so forgetting to lowercase before matching against
  it lets e.g. "YouTube" (capitalized) slip past a guard meant to catch it.

## Round 3: the real phone-pairing bug (root cause, not just the WhatsApp symptom)

The user kept hitting "No pairing request right now" even on a genuinely fresh "connect my phone" attempt. Root
cause, confirmed by reading `phone_devices.json` directly (not guessed): **`start_phone_pairing()` only ever
generates a real pairing code (`begin_pairing()`) the very first time, ever — `if phone_server.registry.list():
return start_phone_session()`.** Once any phone has paired, EVERY later "connect my phone" tries to reach it by
push notification instead, no matter what the user's actual intent is (reconnect that phone, or pair a new one).
Since no phone in this install had ever actually subscribed to push (`push_subscriptions.json` never existed),
`start_phone_session()`'s fallback used to show a notification-setup-only link with NO pairing code — a phone
scanning that, especially one whose browser doesn't already have saved pairing data, lands on "No pairing request
right now" with genuinely nothing to do. This was a real, reachable product bug, not just the earlier
WhatsApp-in-app-browser issue (though both were in play — the user's screenshot showed both: WhatsApp's in-app
browser AND the no-code fallback).

**Fix** (`start_phone_session()` in app.py): when push reaches nobody AND no relay is configured, generate a
real fresh pairing code (`begin_pairing()`) instead of the bare notification-setup link — scanning the QR then
actually re-pairs. When a relay IS configured, kept the OLD behavior (relay's notification-setup link) since a
phone away from this Wi-Fi needs that, not a local-only pairing code — a local code would silently not work for
it. Caught via `tests/test_phone_app.py`'s existing `test_starting_a_session_with_no_reachable_phone_shows_a_qr_code`
(relay case), which broke on my first attempt at this fix before I added the `RELAY_URL` branch — good reminder
that this file already had good coverage of the fallback shape, I just missed it on the first pass. Added
`test_unreachable_phone_without_a_relay_gets_a_real_working_pairing_code` to lock in the new behavior.

**Round 3 correction (that first fix never actually ran):** `settings.py` gives `JARVIS_RELAY_URL` a DEFAULT
(`wss://jervis-relay.onrender.com/`), so `RELAY_URL` is effectively never empty and the "no relay" branch was
dead code for every real install. Found from `logs/actions.jsonl` (the new action log): every real "connect my
phone." after the fix still got the old "tap Enable notifications" reply. Final fix: when the push reaches no
phone, ALWAYS issue a fresh local pairing code, relay or not — "connect my phone" is said at the computer, so the
phone is on the same Wi-Fi; a phone with saved pairing goes straight to chat from that link (`saved()` is checked
before the code), one without pairs again. Old test asserting the relay link was the bug encoded as a test —
rewritten. New `test_the_reported_bug_end_to_end_stale_phone_default_relay_bare_link` reproduces the exact state
over a real websocket; verified it FAILS with the old branch put back and passes with the fix.

**Lessons:** (1) check settings.py defaults, not just .env, before reasoning about config; (2) read
`logs/actions.jsonl` and `logs/jarvis.log` for what really happened before theorizing; (3) a real-browser check
is possible: Playwright (python, Chromium) is in the venv — start `sync_playwright()` BEFORE
`sandbox.install()`, since the sandbox replaces `subprocess` and the driver hangs otherwise. Verified flow: bare
address → "Jarvis wants to pair with this phone." → Confirmed → relay sync round trip → chat → typed "set a timer
for 1 minute" → "Timer set for 1 minute." bubble. After pairing, the chat uses the LOCAL address
(`connectSession(null)` → `location.host`), not the relay.

## Round 4: chat stuck on "Connecting…" after pairing (secure-context bug)

After pairing worked, the phone chat sat on "Connecting…" forever. Root cause: `phone_client.html` encrypts the
chat with WebCrypto (`crypto.subtle`), which browsers ONLY expose on secure contexts (HTTPS or localhost). A phone
always opens `http://<Mac's Wi-Fi IP>:8766` — insecure — so `crypto.subtle` is undefined, `importKey` throws inside
the async `onmessage` handler (swallowed), `auto_attach` is never sent. My earlier Playwright check MISSED it
because it loaded `http://127.0.0.1`, which counts as secure. **Always browser-test the phone page at the Wi-Fi IP
(this Mac: 192.168.1.159), binding the test server to 0.0.0.0** — that reproduced it exactly.

Fix: inlined `@noble/ciphers` 2.4.0 AES-256-GCM (gcm only, esbuild IIFE, 9 KB, MIT; exposes `globalThis.nobleGcm`)
as a separate `<script>` before the main one; `importKey`/`encryptEnvelope`/`decryptEnvelope` use it when
`crypto.subtle` is missing (key becomes `{raw: Uint8Array}`), WebCrypto otherwise. `crypto.getRandomValues` works
on insecure pages, so nonces stay random. Protocol/server unchanged. Verified byte-compatible both ways with
`phone_crypto.py` (incl. Hebrew text, tamper rejection); `tests/test_phone_crypto.py::
test_the_phone_pages_built_in_aes_gcm_interoperates_with_this_module` extracts the inlined bundle and runs it in
Node (skips without node). Also: a failure in the hello_ok step now shows "Couldn't start the chat: …" instead of
hanging. Rejected alternatives: self-signed HTTPS (iOS refuses it, wss fails silently); dropping encryption on the
local link (silent security downgrade). Known limit: getUserMedia/MediaRecorder also need a secure context, so
the phone's hold-to-talk mic button is hidden on the Wi-Fi address — typed chat is the supported path there.

Re-pairing the same phone always adds a brand-new `device_id` to the registry (`DeviceRegistry.add()` has no
dedup/replace-existing logic) — pre-existing behavior, not something this fix introduced or changed. Orphaned
old entries for a repeatedly-re-paired phone will accumulate over time; not fixed this session, worth knowing.
